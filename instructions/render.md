# Producing the output

Every output is a rendering of the same adapted material. There is no
per-modality pipeline and no per-modality re-adaptation — that is what makes
covering very different disabilities tractable instead of five separate projects.

The application renders. This file says what each modality has to get right.

| Output | Driven by |
|---|---|
| Accessible HTML | Always |
| Print PDF | Always. This is what reaches the classroom |
| Braille-ready plain text | No functional vision |
| Audio | No functional vision, or decoding as a total barrier |
| The adaptation report | Always |

Ask which are needed. Do not produce all of them by default.

## Presentation comes from the barriers

Type size, line spacing, line length, contrast, density and whether one task
appears per page are derived from the axis levels — never hand-set per learner,
and never from anything else in the profile. If a learner needs something the
template cannot express, that is a template change, contributed back.

## It has to survive the photocopier

Material reaches a class through a black-and-white school copier. Colour-coded
structure collapses into identical greys, and a "high contrast" version can come
out worse than the plain one. Nothing may carry meaning by colour alone.

## Non-visual output

- Decorative figures are dropped.
- Informative figures become their short description.
- Essential figures become their long description. **An essential figure with no
  long description blocks the render** — an exercise the learner cannot possibly
  answer is worse than no sheet at all.
- Formulae are voiced from their notation, not read as symbols.
- In audio, the item number is announced before each exercise and there is a
  pause after the question.

## The draft mark

Every rendered file carries a visible pending-review mark. Rendering never
removes it. It comes off in exactly one place — the review step, after a human
has signed off — and that is enforced by the application, not asked of you.
